# USB 与网络诊断固件使用说明

调试入口为 `lwip_ch390d_f072/Port/Inc/retarget.h` 中的 `USB_PRINTF_ENABLE=1`。`USB_DIAG_ENABLE` 默认随该宏启用，也可单独定义为 0，仅保留普通 printf。诊断计数由 `Port/Inc/usb_diag.h` 定义，变量名为 `usb_diag`。

USB 接收中断只记录数据和计数，诊断文字由主循环输出。三类状态行每秒轮换输出一条，同一类约每 3 秒出现一次。端点未就绪、发送仍忙、有待发数据或待处理命令时，本轮诊断输出推迟；不能将日志未出现直接等同于 MCU 停机。

## 操作步骤

1. 编译并下载启用 USB printf 的固件，用串口助手打开对应 CDC COM 口。波特率不影响原生 USB 速度。
2. 开启 HEX 发送，关闭自动循环发送，每隔约 1 秒发送一次 `FE A4 00 00 00 00 00 FF`，连续测试 20 次。
3. 接收包含 ASCII 日志和二进制回复，建议保存原始接收数据或 HEX 日志。单次正常查询有四帧，共 32 字节：A0 模式、A1 IP、A2 掩码、A3 网关。诊断文字不能按协议回复解析。
4. 保存从上电至失败后约 10 秒的日志，重点对比失败前后计数变化。若所有周期日志也停止，使用 SWD 暂停并查看调用栈及 `usb_diag.phase`。

## RX 行：接收与派发

示例：

```text
[RX t=4000] p=1 b=8 f=1 d=1 q=1 ow=0 bad=0 n=8 data=FEA40000000000FF
```

| 字段 | 含义 |
| --- | --- |
| t | HAL 毫秒时基，以下时长也均为 ms |
| p / b | 收到的 USB 数据包数 / 字节数；USB 包边界不是命令边界 |
| f | 已解析的完整 8 字节帧数 |
| d / q | 主循环派发的 USB 命令数 / 其中 A4 查询次数 |
| ow | 解析新帧时旧命令标志仍置位的次数，表示存在单命令槽覆盖 |
| bad | 因帧头或帧尾错误而跳过的字节数 |
| n / data | 最近一个 USB 数据包的长度 / 前 8 字节；拆包时不代表整条命令 |

发送后 p、b 不增加，说明未进入应用 USB 接收回调，应检查 COM 口、主机写入和 OUT 端点。p、b 增加但 f 不增加，检查原始字节与帧头帧尾。f 增加但 d、q 长时间不增加，检查主循环阻塞；ow 增加说明未处理命令被新帧覆盖。

## TX 行：回复与端点

```text
[TX t=5000] rsp=32 fail=0 submit=5 busy=0/2 drop=0 init=1/0 latency=0
```

| 字段 | 含义 |
| --- | --- |
| rsp | 成功进入发送队列的协议回复总字节数；日志不计入。单次 A4 通常增加 32 |
| fail | 协议回复入队失败次数；业务函数仍沿用原有错误处理 |
| submit | 成功提交至 CDC 驱动的传输次数，包含日志；不代表主机应用已经读取 |
| busy | 当前观察到的连续发送忙时长 / 历史最长发送忙时长。状态行只在空闲时输出，因此当前值通常为 0 |
| drop | 因调试发送空间不足而丢弃的日志字节数 |
| init | CDC 配置初始化次数 / 反初始化次数，用于观察重新配置 |
| latency | 完整帧被解析到主循环派发之间的历史最大时长；覆盖时只能对应最新帧 |

q 增加、rsp 未增加且 fail 增加，说明协议回复未能入队。rsp 增加但 submit 长时间不推进，检查 CDC 发送忙、USB 设备状态和主机接收。submit 已推进仍未在串口助手看到回复，需要继续检查 USB IN 完成及主机侧数据，不能仅凭 submit 判断已送达。

调试输出复用已有 256 B 队列，但保留最后 32 B 给协议回复。日志不等待队列空间，也不在 USB 中断里 printf。该预留不构成命令队列或持续高负载下的无丢失保证。

## NET 行：耗时与硬件快照

```text
[NET t=6000] max=1/0/1/0 wait=0 out=1 tx=2 down=0 to=0 tcr=00 spimax=1 spierr=0 hal=0 reg=01:00 id=0000:0000 nsr=00 rst=00000000
```

以上仅为字段格式示例，ID 和状态值不是期望读数。

| 字段 | 含义 |
| --- | --- |
| max | 主循环网络任务 / 网卡中断处理及 TCP 派发 / lwIP 定时处理或 DHCP 分支 / USB 业务处理的历史最大耗时 |
| wait | CH390 TCR TXREQ 忙等待的历史最大时长 |
| out | 单次网卡 linkoutput 完整发送过程的历史最大时长，包含写 SRAM 和 TXREQ 等待 |
| tx | 网卡 linkoutput 累计调用次数，包含 ARP、TCP 等网络发送 |
| down | 因实际链路断开而拒绝的网卡发送次数，拒绝时不写 TX SRAM |
| to | TXREQ 状态等待超过 100 ms 的次数 |
| tcr | 最近检查的 TX 控制寄存器，bit0 为 TXREQ |
| spimax | 单次 HAL SPI 字节传输的历史最大时长 |
| spierr | HAL SPI 传输返回非 HAL_OK 的累计次数 |
| hal | 最近一次 SPI 错误状态：1=HAL_ERROR，2=HAL_BUSY，3=HAL_TIMEOUT；0 表示未记录错误 |
| reg | 最近读取的 CH390 寄存器地址与读回值 |
| id | 网络初始化后的 CH390 VID / PID 只读快照；持续全 0 或全 FFFF 值可疑，需要核对供电、SPI 与器件规格 |
| nsr | 最近读到的 CH390 NSR，不保证是打印瞬间的链路状态 |
| rst | 启动时 RCC CSR 复位标志快照，未主动清除或更改复位标志 |

出现明显的秒级 max 或增长的 spierr，应结合具体调用栈检查 SPI、CH390 发送等待或链路事件。网卡发送在写 SRAM 前检查真实链路并等待前一帧完成。链路断开返回 ERR_IF，TXREQ 状态等待超过 100 ms 返回 ERR_TIMEOUT；不自动重置网卡。该限制不包含每次 SPI 调用自身的 HAL 超时，不等同于整个定时器调用最多 100 ms。命令协议保持不变。

## 日志停顿时的 SWD 定位

| usb_diag.phase | 所在阶段 |
| --- | --- |
| 0 | 本轮处理结束 |
| 1 | 网络初始化（含启动硬件读取） |
| 2 | 网卡中断处理及 TCP 命令派发 |
| 3 | lwIP 定时器或 DHCP 分支 |
| 4 | USB 命令处理 |
| 5 | USB 发送轮询 |
| 6 | 诊断报告生成 |
| 7 | CH390 TCR TXREQ 忙等待 |
| 8 | CH390 linkoutput 发包（TXREQ 等待期间切换为 7） |

结合 `HAL_GetTick()` 与 `usb_diag.phase_since_ms` 的差值判断是否长期停留。若卡在某阶段，主循环不能输出后续状态行，历史 max 也要在该阶段返回后才更新。此时应查看调用栈，不能把最近一条日志当成阻塞位置。

诊断计数和部分状态由中断与前台更新，日志用于趋势定位；需要一致的精确现场时，用 SWD 暂停后检查。日志仍会影响执行时间，最终性能以关闭诊断后的目标板测试为准。
## 定时器阶段长停顿的判断

若 max 的第三项达到数秒，比较 wait、out、spimax：wait 与其接近，表示已确认停顿主要发生在 TXREQ 等待；out 很大而 wait 很小，则检查 SRAM 写入、SPI 时间及中断负载；两者均小，则进一步排查定时器处理数量、时基和其他回调。wait 和 out 是单次调用峰值，多个调用叠加时可能小于整个定时器阶段的峰值。

NSR 的 bit6 为链路状态；nsr=80 表示该次读数链路位为 0。寄存器和计时记录只代表采样与返回后的现场，不能代替实时调用栈。

链路未建立时，down 增长而 wait、out 维持较小值是预期现象；这只隔离了网络发送对 USB 的拖延，并不代表物理网络已经修复。仍需检查 CH390 与路由模块之间的供电、启动和链路。

## UDP 能发现但多次 TCP 连接后超时

UDP 发现使用 8888 端口，控制连接使用 TCP 23000。UDP 能实时收到 DISCOVERHOST 只证明该次网络收发成功，不代表 TCP 连接资源可用。

TCP 活动 PCB 池为 3。服务端收到对端 FIN 时必须调用 tcp_close()，否则连接遗留在 CLOSE_WAIT 中，重复连接后可能耗尽池；UDP 仍可继续回复。上位机连接测试以及每次开关 IO 时都会创建、关闭 TCP 连接，因此关闭处理必须完整。当前服务端 FIN 分支调用 tcp_close()，由 lwIP 处理关闭与资源回收。

验证时在重启或下载固件后，连续测试连接与断开超过 3 次（建议 20 次），并确认 UDP 发现仍可用。单纯重启旧固件只能暂时释放资源，不能修复关闭分支缺陷。
